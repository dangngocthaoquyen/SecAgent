# Controlled DVAA ASI01 text batch (Phases B4.1 and B4.4B Step 2)

This is an opt-in runtime integration, verified offline with mock HTTP transport. SecureBot has **not** passed a live GH-C01 control. The server-owned text-target policy admits only exact, reviewed, revision-matched DVAA profiles: ResearchBot at `http://127.0.0.1:7015/v1/chat/completions`, model `researchbot`, and SecureBot at `http://127.0.0.1:7001/v1/chat/completions`, model `securebot`. Both require `openai-chat`, a timeout of at most 30 seconds, and no credential alias. The endpoint port selects the DVAA agent; the request model does not route to another port. Target Management can save other targets but cannot extend this execution policy. Startup without the explicit ASI01 batch flag retains the existing GH-C01 one-click path and leaves batch routes disabled. The synthetic batch service remains separate and mock-only.

The shared payload file is `payload/goal_hijacking.yaml`. GH-C01, GH-001 and GH-002 asset SHA-256 values are pinned in `workflow.asi01_batch`; a changed file prevents startup or dispatch until the binding is reviewed. Each input is rendered from the existing payload template and YAML variables. The selected target's reviewed endpoint identifies the DVAA agent; no web-fetch action is requested for the three text cases. The HTTP adapter observes response text and transport completeness. It does not claim internal tool or web actions.

The existing native YAML marks the text cases as hybrid-capable and supplies a goal-hijacking semantic contract. This B4.1 batch activates **rule-only** evaluation. Rule-only cannot classify paraphrased adoption or mixed compliance; these remain INCONCLUSIVE. Backend-driven hybrid evaluation needs a separately reviewed batch Judge budget and actual Judge progress instrumentation before it is selectable here. No Pi process is invoked by this slice.

## Baseline, authorization and reporting

The server reorders a selected batch to run GH-C01 first. GH-001 and GH-002 are blocked if GH-C01 is absent, and are recorded as `clean_baseline_not_confirmed` with no request or verdict if its observed final verdict is not PASS. This is necessary because the previously saved ResearchBot GH-C01 run returned a generic greeting instead of the requested project summary. That historical observation does not establish the legitimate task baseline for this agent. It is not modified by this phase.

The local operator first reviews the exact profile revision. The batch preview binds ordered IDs, pinned asset/input hashes, policy revision, target revision and request budget into a plan hash. A confirmed start creates one short-lived case-scoped `ExecutionGrant` per ready case under the existing policy cap; each case claim is exclusive. `OneRequestHttpClient` reserves at most one exact-URL POST per case, rejects redirects, caps response bytes and timeout, and never retries. The `BatchOrchestrator` enforces total budget, sequential execution, durable state, cancellation of remaining cases, and no concurrent batch. The existing GH-C01 dispatcher allowlist and `AdmissionPolicy.max_testcases=1` remain unchanged; this opt-in service has its own three-text-case allowlist.

Each executed case gets a native report and `run-summary.json` under the configured controlled-run root. Its sanitized runtime snapshot includes testcase and payload hashes, input and evaluation hashes, target/profile identity, exact submitted public input, original goal, request mapping, timeout, evidence provenance and evaluation mode. The Runner report retains observation completeness, final rationale, and Judge status (`null` for rule-only). Report hashes and run identities are checked by the existing Reporting API. Blocked, unsupported and cancelled records have no security verdict or report link.

## Local startup and acceptance boundary

After separate operator approval for a live acceptance, `python start_secagent_local.py --enable-asi01-batch` enables the controlled ASI01 text service at startup. The flag alone does not approve a target or send a request and does not enable the guarded Web Lab. In Target Management, create `dvaa-securebot` on platform `dvaa`, endpoint `http://127.0.0.1:7001/v1/chat/completions`, model `securebot`, protocol OpenAI-compatible chat, timeout 30 seconds. Validate and save. Confirm authorization for the exact current revision through the first benign connection probe, then validate the target configuration. For a one-case control, select only GH-C01 and click **Run Selected Tests**. For a three-case batch, select GH-C01, GH-001 and GH-002 and click once. A previously saved standalone GH-C01 PASS does not unlock later attack cases: GH-C01 must pass and persist in the same batch. Existing same-origin, nonce and local operator authentication checks remain in force. The default `python start_secagent_local.py` does not enable this batch service.

For offline verification, `backend/tests/test_asi01_batch.py` and `frontend/browser-tests/asi01-batch-real-api.spec.ts` use `httpx.MockTransport` with the native assets, real Workflow API, BatchOrchestrator, Runner, report writer, Reporting API and frontend. No live target or Judge is contacted. The browser test uses temporary output and an isolated API fixture.
